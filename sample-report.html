AI-Built App Security Checkup — Sample Audit Report

Prepared by: CapAIGC Security Review Subject: "TaskFlow" — demo SaaS application (Next.js 13 + Supabase) Report type: Static source-code security audit (sample report) Date: 2026-11-12 Scope: 8 source files, ~94 lines — client setup, auth library, 3 API routes, 1 component, database schema, dependency manifest

Sample report notice. This report was produced on a deliberately vulnerable demo codebase written for evaluation purposes. It is not a real client engagement. It demonstrates the exact format, evidence standard, and depth of a paid checkup: every finding below cites a real file and line, was independently re-verified by a human reviewer before inclusion, and ships with a fix prompt you can paste into your AI coding tool.

Executive summary

Overall risk: Critical. Security score: 17 / 100.

The application ships a full-access database key to every visitor's browser, has Row Level Security switched off on the table that stores user emails, and performs no authentication on endpoints that read profiles and accept file uploads. An unauthenticated attacker can read user PII and write files to the web root with no credentials at all. Do not deploy this code.

Fix first (in this order): C1 → C2 → C3 → H1. These four close the unauthenticated data breach and file-write paths.

Findings

C1 — Supabase service-role key exposed in the browser bundle

  • Severity: Critical
  • Evidence: lib/supabaseClient.ts:6 — process.env.NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY!
  • Impact: Next.js inlines every NEXT_PUBLIC_* value into client JavaScript. The service-role key bypasses Row Level Security entirely: anyone who opens the page source can read and modify every table and storage object.
  • Remediation: Use the public anon key in browser code. Keep the service-role key in a server-only variable (no NEXT_PUBLIC_ prefix), and rotate the exposed key now — treat it as compromised.
  • Fix prompt (paste into Cursor / Claude Code): "In lib/supabaseClient.ts, replace NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY with NEXT_PUBLIC_SUPABASE_ANON_KEY. Then grep the repo for SERVICE_ROLE and confirm it only appears in server-side code (API routes / server components)."

C2 — Row Level Security disabled on profiles

  • Severity: Critical
  • Evidence: supabase/schema.sql:9 — alter table profiles disable row level security;
  • Impact: profiles stores full_name and email. With RLS off, any client holding the anon key can read or write all rows — there is no per-user isolation. Combined with C1 this is full profile-data compromise.
  • Remediation: Enable RLS and add owner-scoped policies (using (auth.uid() = id) for select/update; inserts restricted to the authenticated owner).
  • Fix prompt: "In supabase/schema.sql, enable row level security on profiles and add policies so a user can only select and update the row where id = auth.uid(). Remove the disable statement."

C3 — Unauthenticated file upload with path traversal

  • Severity: Critical
  • Evidence: app/api/upload/route.ts:10-11 — path.join(process.cwd(), "public/uploads", file.name) then writeFile(dest, bytes); the handler performs no authentication or validation.
  • Impact: Anyone can write arbitrary files into the public web root. A crafted filename containing ../ may escape the uploads folder (parser behaviour requires manual confirmation); HTML/SVG uploads are served same-origin and execute script in visitors' browsers.
  • Remediation: Require an authenticated session; generate a random server-side filename; allowlist extensions/MIME types and reject path separators; store files in private object storage, not the web root.
  • Fix prompt: "Rewrite app/api/upload/route.ts: reject unauthenticated requests (401), validate the file extension against an allowlist (png, jpg, pdf), cap size at 5 MB, save with a random UUID filename, and never use the client-supplied filename in a filesystem path."

H1 — Unauthenticated IDOR in the profile API

  • Severity: High
  • Evidence: app/api/profile/route.ts:11-15 — reads userId from the query string and queries with a service-role client; no session check anywhere in the handler.
  • Impact: GET /api/profile?userId=<any-id> returns that user's name, email, plan and signup date. IDs are enumerable/leakable; the service-role client bypasses RLS, so nothing limits the read.
  • Remediation: Derive the user from a verified session; reject requests where the session user does not match the requested ID, unless a server-verified admin role is present.
  • Fix prompt: "In app/api/profile/route.ts, authenticate the request first and return 401 if there is no valid session. Only allow the request if session.user.id equals the requested userId or the session carries a verified admin role."

H2 — JWT fallback secret, tokens that never expire

  • Severity: High (Critical in any deployment where JWT_SECRET is unset)
  • Evidence: lib/auth.ts:3 — process.env.JWT_SECRET || "changeme-dev-secret"; lib/auth.ts:7 — jwt.sign(...) with no expiresIn; lib/auth.ts:13 — ignoreExpiration: true.
  • Impact: If the environment variable is missing, the signing secret is a public constant — anyone can forge a token for any user. Tokens also never expire, and verification is explicitly told to ignore expiry, so a leaked token is a permanent credential.
  • Remediation: Crash on startup when JWT_SECRET is absent; use a high-entropy secret; set a short expiresIn (e.g. 1h access tokens); remove ignoreExpiration.
  • Fix prompt: "In lib/auth.ts, throw at startup if JWT_SECRET is not set, remove the fallback value, add expiresIn: '1h' to jwt.sign, and remove ignoreExpiration from jwt.verify."

H3 — Admin authorization via a client-controlled header

  • Severity: High
  • Evidence: app/api/admin/route.ts:5 — if (req.headers.get("x-admin") !== "true")
  • Impact: Headers are set by the caller. curl -H 'x-admin: true' unlocks admin statistics (user counts, MRR). Any "admin" check based on request input is decoration, not authorization.
  • Remediation: Authenticate the session and check a server-side role/claim issued at login.
  • Fix prompt: "In app/api/admin/route.ts, replace the x-admin header check with session authentication plus a server-side role check (session user role must equal 'admin', set only by our own auth flow)."

H4 — Stored XSS via unsanitized comment HTML

  • Severity: High
  • Evidence: components/Comment.tsx:3 — <div dangerouslySetInnerHTML={{ __html: html }} />
  • Impact: If html carries user-submitted comment content (data source requires manual confirmation — no sanitizer exists anywhere in the reviewed code), an attacker stores script that runs in every reader's browser: session theft, actions taken as the victim.
  • Remediation: Sanitize with an allowlist sanitizer (e.g. DOMPurify) before rendering, or render comments as plain text; add a restrictive Content-Security-Policy.
  • Fix prompt: "In components/Comment.tsx, sanitize the html prop with DOMPurify (default allowlist) before passing it to dangerouslySetInnerHTML."

H5 — Public storage bucket for user documents

  • Severity: High
  • Evidence: supabase/schema.sql:11-15 — policy "public read" on storage.objects for bucket user-docs, and the bucket created with public = true.
  • Impact: Every object in user-docs is world-readable to anyone with its URL. User documents are typically the most sensitive files an app holds.
  • Remediation: Make the bucket private, drop the public SELECT policy, add owner-scoped policies, and serve files through short-lived signed URLs.
  • Fix prompt: "In supabase/schema.sql, set the user-docs bucket to private, remove the public read policy, and add a policy allowing users to read only objects under their own user-id folder."

M1 — Outdated dependencies, including a known-vulnerable lodash

  • Severity: Medium
  • Evidence: package.json:6,9,10 — next 13.4.19, jsonwebtoken 8.5.1, lodash 4.17.20.
  • Impact: lodash 4.17.20 is affected by CVE-2021-23337 (command injection in template) and CVE-2020-28500 (ReDoS), both fixed in 4.17.21; exploitability depends on whether untrusted input reaches those functions (requires manual confirmation). The other two packages are stale and outside their support windows.
  • Remediation: Upgrade lodash to ≥4.17.21; add npm audit to CI; schedule upgrades for Next.js and jsonwebtoken with compatibility testing.

Scope, method, and limits

Method: Full manual read of every in-scope file (cross-file data-flow review), followed by independent re-verification of each finding's file/line evidence by a second reviewer. AI-assisted analysis with human review of every reported item.

Not covered by a static checkup: runtime/dynamic testing of the deployed app, dependency installation and npm audit execution, Supabase project settings beyond the provided schema, environment variables and deployed secrets, middleware and code not provided, infrastructure and DNS/TLS configuration. Items that depend on runtime behaviour are labelled "requires manual confirmation" rather than reported as confirmed.

What a clean report means: no confirmed findings in the reviewed scope — never a guarantee that an application is "secure".
